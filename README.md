On-chain contracts for [Curvy](https://docs.curvy.box/for-the-curious/) — private payments
built on stealth addresses and zero-knowledge proofs. Funds arrive at a per-recipient
address nobody can link to the recipient, are shielded into notes, and are spent through
Groth16-proved aggregations that reveal neither sender, recipient, nor amount.

Two independent trees live here, one per execution environment:

| | | |
|---|---|---|
| [`evm/`](evm) | Solidity | Vault, aggregator, portal factory and verifiers. Hardhat 3 + Ignition. |
| [`solana/`](solana) | Rust | The `curvy-portal` Anchor program — deterministic vault PDAs that bridge to the EVM aggregator. |

Each has its own README with the toolchain, build and deploy instructions; start there.

## Architecture in one paragraph

Curvy is a hub-and-spoke design. Exactly one chain runs the **aggregator** — the shielded
pool that holds balances, tracks the note commitment tree, and verifies aggregation,
withdrawal and batch-commitment proofs. Every other supported chain runs only a **portal
factory**, which deploys the deterministic per-recipient portals that receive deposits and
bridge them to the aggregator chain. Solana is one of those spokes, which is why its
program mirrors the portal contract rather than the aggregator.

In production the aggregator chain is Arbitrum; Base, BSC, Ethereum, Gnosis, Linea,
Optimism, Polygon and Tempo are portal-only. Deployed addresses for every environment and
network are committed under
[`evm/ignition/deployments/`](evm/ignition/deployments) as
`<environment>_<network>_v2/deployed_addresses.json`, alongside the Ignition journal and
the exact build-info that produced the bytecode.

V2 is greenfield — it is not an upgrade path from V1. The V1 contracts remain in
`evm/src/v1/` and their frozen launch modules in `evm/ignition/modules/legacy/` because the
live V1 proxies still need their journals to reconcile.

## Generated consumers

Both the TypeScript ABIs and the Rust bindings are generated from the *same* compiled
Hardhat artifacts that the Ignition deploy pipeline ships — so what a client calls is what
is actually deployed, rather than a second, independent build of the same sources:

- **Rust** — [`evm/rust/curvy-bindings`](evm/rust/curvy-bindings), an
  [alloy](https://github.com/alloy-rs/alloy) binding crate published to crates.io. It
  commits no generated Rust; `sol!` expands vendored artifacts at compile time, and
  `artifact-manifest.json` records the source commit, compiler settings and a SHA-256 per
  artifact.
- **TypeScript** — ABIs extracted into the Curvy SDK by `evm/scripts/extract-abis.ts`.

`evm/artifact-registry.mjs` is the single source of truth mapping a logical contract id to
its artifact path and fully qualified name, shared by both extractors and every Ignition
module.

## Licensing

There is no single repository-wide license — check the SPDX header of the file you intend
to use. In summary:

| License | Applies to |
|---|---|
| `Apache-2.0` | The core V2 contracts: vault, aggregator, portal, portal factory |
| `GPL-3.0` | The Groth16 verifiers (generated by snarkjs, which emits GPL) |
| `BUSL-1.1` | `ICurvyVerifiers.sol` and its V1 counterpart |
| `AGPL-3.0-only` | The vendored `ICreateX.sol` interfaces (upstream CreateX license) |

The `curvy-bindings` crate is `GPL-3.0-only`, because it distributes verifier ABIs and
bytecode. The Solana program carries its own terms — see [`solana/`](solana).

## Security

The V1 vault, aggregator and portal factory deployed by
[`evm/ignition/modules/legacy/`](evm/ignition/modules/legacy) were audited before launch.
